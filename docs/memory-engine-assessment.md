# Personal Language Memory Engine v0.1 — 需求评估

> 评估对象：你提供的《Personal Language Memory Engine v0.1》HTML 规格
> 评估基准：已交付的 `love` M1（Go CLI，已发布 v0.1.0）
> 结论：**方向正确，但当前形态不可直接实施**——核心算法缺失、反馈闭环自相矛盾、数据模型与现状冲突、认知预算在数学上不成立。

---

## 0. 评分卡

| 维度 | 评分 | 一句话理由 |
|---|---|---|
| 产品定位 | **A** | local-first + 认知预算 + AI 只做内容，三个判断都对 |
| 架构方向 | **B** | 分层清晰，但把"常驻 daemon"和"邮件反馈"当成了前提 |
| 可实施性 | **C−** | 反馈通道、调度、SMTP 凭据、可达性均未定义 |
| 数据设计 | **C−** | 与已交付 schema 冲突，且缺事件表、缺约束 |
| 算法完备性 | **D** | 名为 Memory Engine，但没有间隔重复算法 |
| 验收可测性 | **D** | "连续运行 30 天"无法自动化验证 |

**一句话总结**：现在这份规格描述的是一个**每天发邮件的工具**，还不是一个**记忆引擎**。缺的那一块（调度算法）恰好是唯一不可省略的核心。

## 1. 硬伤：与已交付的 `love` 数据模型冲突

规格假设 CLI 写的是 `dict.jsonl`：

```json
{"word":"maintain","meaning":"维护","source":"browser","created_at":"2026-09-13"}
```

`love` M1 实际写的是 `~/.ewh/words.jsonl`：

```json
{"word":"evil","ipa":"/ˈiːvəl/","eli5":"Very, very bad.","chinese":"邪恶的"}
```

| | 字段 |
|---|---|
| 现有实现 | `word` `ipa` `eli5` `chinese` |
| 规格假设 | `word` `meaning` `source` `created_at` |
| **规格丢掉的** | **`ipa`、`eli5`** |
| 规格新增的 | `created_at`、`source`、`meaning`(=`chinese` 改名) |

**这不是命名分歧，是功能倒退。** `eli5`（三岁小孩能懂的英文解释）是整个产品最花心思、也最难被普通词典替代的部分，`ipa` 是发音基础。规格把它们删了，等于把 `love` 降级成一个普通词表。

另外两点：

- **`source: "browser"` 指向一个并不存在的组件。** 全盘扫描确认没有任何浏览器扩展代码，也没有 `dict.jsonl`。v0.1 里 `source` 只能是 `cli`。要么写进需求、要么删掉。
- **`created_at` 值得加**，但它的语义要定清楚：是"加入词库时间"还是"首次学习时间"？这两者对调度影响不同。

**建议**：以现有 schema 为**超集**扩展，不要替换。

```
words = word, ipa, eli5, chinese, created_at, source(v0.1 固定 "cli")
```

## 2. 硬伤：记忆引擎的核心算法完全缺失

规格里最响亮的一句是：

> AI 负责内容生成，不负责替代记忆算法。

这个判断**完全正确**。但问题是——**算法本身从头到尾没有被定义**。

### 缺什么

| 缺口 | 说明 |
|---|---|
| 间隔怎么算 | 从未定义。没有间隔就没有间隔重复。 |
| `strength` 是什么 | 0–100？怎么从一次反馈更新？没有公式。 |
| 状态转移条件 | `NEW→LEARNING→FAMILIAR→MASTERED` 每一步的门槛都没写。 |
| 复习历史 | `success_count`/`fail_count` 是**计数器**，不足以驱动 SRS。SM-2 需要 ease factor 与上次间隔；FSRS 需要 stability/difficulty 与每次复习的 (间隔, 结果)。必须补 `reviews` 事件表。 |
| 遗忘回退 | 生命周期图画成**单向流水线**。但记忆必然遗忘：一个 MASTERED 的词答错了就该降级。当前状态机无法表达这件事，与记忆规律直接矛盾。 |

### 另一个结构性问题：两套并行状态

`status`（字符串）和 `strength`（数值）是**两份互相独立的状态**。它们一定会不一致（`status=FAMILIAR` 而 `strength=5`）。必须指定唯一真相源，另一个由它派生——否则每次修 bug 都要先问"以哪个为准"。

### 建议

不要自创算法，选一个公开标准，并把接口做成可替换：

| 方案 | 复杂度 | 适合度 |
|---|---|---|
| **Leitner 盒子**（1/2/4/8/16 天） | < 100 行 | ✅ **推荐 v0.1** |
| SM-2（Anki 早期） | 中等 | ✅ 可选，3 档反馈可直接映射 |
| FSRS-5 | 高 | ⏳ v0.3，参数开源但过重 |

反馈三档到算法的映射（SM-2）：`已掌握→5`、`模糊→3`、`忘记→1`。

> FSRS 用 4 档（Again/Hard/Good/Easy）。如果将来要上 FSRS，现在就该把反馈设计成 4 档，避免以后改邮件模板和数据库。**这是个需要现在决定的小事，以后改很贵。**

### 关键工程约束：时间必须可注入

调度逻辑必须接收一个 `clock` 接口而不是直接调 `time.Now()`。否则：

- 无法写确定性测试
- "连续运行 30 天"的验收无法自动化

这一条是可测试性的前提，必须在写第一行代码前定下来。

## 3. 硬伤：认知预算在数学上不成立 ⭐

这是我认为**最有价值的发现**。规格写：

```
默认每日：新词 2 个 / 复习 3 个 / 总量 <= 5 个
```

稳态下有一个恒等式：**每天新增的词，最终都要被复习 R 次**（R = 一个词从 NEW 到 MASTERED 需要的复习次数）。所以

```
稳态每日复习量 = 每日新词数 × R
```

按 Leitner 5 盒（1/2/4/8/16 天），R ≈ 5：

| 新词/天 | 每词复习次数 R | 稳态复习量/天 | 规格预算 5/天够吗 |
|---|---|---|---|
| 2 | 5（Leitner 5 盒） | **10** | ❌ 超一倍 |
| 2 | 3（Leitner 3 盒） | **6** | ❌ 仍超 |
| 2 | 1.5（规格隐含） | 3 | ✅ 但 R=1.5 意味着复习一两次就"掌握" |
| 1 | 5 | 5 | ✅ 合理 |
| 0.6 | 5 | 3 | ✅ 与 3 复习/天自洽 |

**结论**：`2 新 + 3 复习` 隐含"每个词只复习 1.5 次"，这在记忆上不成立。要么把新词降到约 1 个/天（或每两天 1 个），要么把复习预算提到 6–10 个/天，要么接受**积压无限增长**。

规格说"目标不是一天记很多，而是一年持续积累"——这个理念正是要求**新词速率必须服从复习承受力**。当前数字违反了它自己的理念。

**建议**：不要硬编码两个数字，让复习预算**主导**新词投放量：

```
每日复习预算 = 8
实际新词量 = max(0, 每日上限 - 今日到期复习数)   // 到期复习优先
新词每日硬上限 = 4
```

## 4. 硬伤：Email 反馈闭环与 local-first 自相矛盾 ⭐

邮件里的 `[已掌握] [模糊] [忘记]` 按钮，用户点下去之后，**请求要发到哪里？**

- local-first ⇒ 没有公网服务器
- 在手机上点邮件按钮 ⇒ **不可能访问你 Mac 上的 `localhost:port`**

这个矛盾是整个架构里最大的未定义点。四条出路，各有代价：

| 方案 | 本地化 | 手机可用 | 代价 |
|---|---|---|---|
| **A. mailto: 回信 + IMAP 解析** | ✅ | ✅ | 需 IMAP 凭据、解析脆弱、有延迟、用户要"发送邮件"而不是"点按钮" |
| **B. 隧道 / 公网端点** | ❌ | ✅ | 破坏 local-first，引入鉴权与运维 |
| **C. 自定义 URL scheme**（`love://grade/maintain/3`） | ✅ | ❌ | 无需服务器，但只在本机点击有效 |
| **D. v0.1 不做邮件反馈** | ✅ | — | 反馈走终端，手机体验放弃 |

### 原建议：把"生成邮件"和"发送邮件"解耦（已被 §4.5 取代）

```
v0.1:  状态 → love daily --html > today.html     ← 纯函数，浏览器里验收
v0.2:  同上  → SMTP 发送                          ← 最后加一层薄适配器
```

这样做的好处：

1. v0.1 **完全不依赖** SMTP、凭据、公网可达性
2. 却已经能验证 **90% 的价值**：内容质量 + 调度正确性
3. 邮件 HTML 变成纯函数 ⇒ 可做 golden 快照测试
4. 发送层失败不影响引擎正确性

### 被低估的邮件工程负担

规格把"HTML Email Generator"当成一个方框，实际它包含：

- **邮件客户端会剥离 `<style>` 里的 CSS**。Gmail 尤其激进。必须用**内联样式 + table 布局**。你规格里那份带 `<style>` 的 HTML 直接发出去会烂掉。
- 必须提供 `multipart/alternative` **纯文本版本**（送达率 + 可访问性）
- SMTP 凭据（Gmail 需应用专用密码）要落本地磁盘，权限 `0600`
- **重复发送保护**（同一天发两次？重试时如何幂等？）
- **退订 / 暂停开关**——一个每天发邮件的东西必须有
- 时区与发送时间（DST 边界）
- 邮件里的反馈链接需要**一次性 token**（防重放、防误点两次）

## 4.5 已定方案：系统待办任务（Reminders）作为推送通道 ⭐

**决策**：放弃 SMTP 邮件，改用 **macOS 自带「提醒事项」** 作为每日推送通道：桌面端生成一条待办，用户回到电脑后**批量精评**。

> ### ⚠️ 重要修正（2026-09-13）
>
> 本节初稿假设用户使用 iPhone，并依赖 **iCloud 把待办同步到手机**。**该假设错误，已作废。**
>
> 本机随后实测：
>
> | 检查项 | 结果 |
> |---|---|
> | Reminders 账号 | **`本地`** —— 未配置 iCloud |
> | Calendar 日历 | `Scheduled Reminders, Birthdays, 中国大陆节假日, Siri Suggestions` —— **全是本地/系统日历** |
> | `~/Library/Calendars` | 空 —— **无 Google / Exchange / CalDAV 账号** |
> | 用户手机 | **Android** —— iCloud 不可用 |
>
> 结论：**跨设备同步不存在，也不能靠 iCloud 实现。**

### 为什么这条通道仍然成立

用户原始诉求是"**让用户回到电脑时再去统一反馈**"——**反馈本来就在电脑上发生**，同步从来不是必需品：

| 原问题 | 这条通道如何解决 |
|---|---|
| 邮件按钮点不到 localhost | 待办只做**提醒**，不承载逐词评分；评分统一在电脑上批量完成 |
| 每日邮件造成压力 | 待办是系统原生条目，可静音可推迟，不产生"未读邮件"焦虑 |
| 跨设备同步 | **不需要**。待办、反馈、算法全部在同一台 Mac 上闭环 |

### 本机实测结果（macOS 27.0）

| 能力 | 路径 | 实测 |
|---|---|---|
| 读取列表 | `osascript` → Reminders | ✅ 返回 `提醒事项` |
| 创建待办（含备注链接） | `make new reminder` | ✅ 返回稳定 ID `x-apple-reminder://EA502978-…` |
| 读回验证 | 按名称查询 | ✅ |
| 写入完成状态 | `set completed to true` | ✅ 读回 `completed=true` |
| 触发本地命令 | `do shell script` | ✅ `bridge-ok` |
| 删除清理 | `delete every reminder` | ✅ 无残留 |

探针已自行清理，未在提醒事项中留下任何数据。

### 关键限制：待办只有 1 bit

一条提醒只有"完成 / 未完成"，而 SRS 需要 3–4 档（已掌握 / 模糊 / 忘记）。硬凑都不好：

| 硬凑方案 | 问题 |
|---|---|
| 一词一条待办 | 每天 5 条，刷屏 |
| 一词三条待办（每档一条） | 每天 15 条，直接劝退 |
| 用户手改标题填档位 | 交互成本高于学习本身 |

**因此采用两层反馈**：

```
第一层（桌面，1 bit，本地）
  一条每日待办： "复习 5 个词（到期 3 + 新词 2）"
  备注里列出今天的词
  它一直挂在「提醒事项」里，直到用户处理 —— 这就是"回到电脑时的提醒"
  勾选 = "今天处理过了"
  → 用途：判断用户是否在场（解决"未响应 ≠ 忘记"）
  → 若用户直接跑了 love review，这一位可由 love daily 自动补勾

第二层（电脑，3–4 档，驱动算法）
  回到电脑后： love review          （终端交互）
              love review --web    （本地页面，浏览器里点选）
  逐词评分，批量提交
  → 用途：产生 reviews 事件，驱动 SRS 调度
```

第一层**不参与算法**，只回答"该不该继续推送"；第二层才产生调度输入。**这样 1 bit 的限制不再是缺陷，反而把"在场"和"掌握程度"两个正交信号干净地分开了。**

### 待办内容示例

```
标题： 英语复习 · 5 个词（到期 3）
备注： maintain 维护 · fragile 易碎 · deploy 部署 …
      回电脑后运行  love review
```

### 如果确实想要手机提醒（Android 可行方案）

纯 Mac 方案不需要任何云端。但若希望**离开电脑时也收到提醒**，Android 侧只有这几条路：

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **A. Google 日历** | 在 macOS「系统设置 → 互联网账户」加入 Google 账户并勾选日历；`love daily` 往该日历写一条全天事件 → Google 原生同步到 Android 日历并推送通知 | 需添加 Google 账户；**单词明文会上传到 Google**，与 local-first 定位冲突 |
| **B. 局域网本地页面** | `love review --web --lan` 绑定 `0.0.0.0`，手机同 Wi-Fi 访问 `http://<Mac-IP>:<port>` | 完全不上云；但要求 Mac 醒着、服务在跑、仅家里 Wi-Fi 有效 |
| **C. 第三方待办 API**（Todoist / TickTick） | Mac 侧调 REST API 建任务，Android 用官方 App | 引入云依赖 + API token，不算"系统自带" |
| **D. 自建 CalDAV** | 自托管 CalDAV，Android 用 DAVx5 | 要运维一台服务，与"不要常驻服务"矛盾 |

**建议**：v0.1 **先做纯 Mac 闭环**（零配置、已验证、零隐私外泄）。手机提醒作为 v0.2 可选项，届时优先评估 **A（最省事）** 或 **B（最保隐私）**。

> ⚠️ 隐私提醒：方案 A 会把单词明文同步到 Google 服务器。这与项目"local-first、词表属于用户"的定位直接冲突，**需你明确同意才做**。

### 必须处理的工程细节

| 项 | 说明 |
|---|---|
| **列表名是本地化的** | 你的机器上叫「提醒事项」，英文系统叫 "Reminders"。**禁止硬编码列表名**，用 `default list` 或做成配置项 |
| **幂等** | 每天只允许存在一条未完成的"今日复习"待办。重跑 `love daily` 必须先查后建，否则刷屏 |
| **陈旧待办清理** | 用户没勾选的昨天待办：更新而非新建，或自动删除。需明确策略 |
| **TCC / 自动化授权（最大风险）** | `osascript` 操作 Reminders 需要「自动化」权限，权限归属**调用方进程**。从终端跑已实测通过；但**从 launchd 后台任务跑可能被拒**（无归属 App）。缓解：后台任务只写文件，Reminders 读写交给用户触发的 `love sync`；或用 `shortcuts run`（权限归属 Shortcuts.app）作为后备 |
| **稳定 ID** | 创建返回的 `x-apple-reminder://…` 存入本地库，后续按 ID 读回，不做名称匹配 |
| **恢复手段** | 同时在备注里埋稳定标记（如 `#love-2026-09-13`），本地库丢失时仍可对账 |
| **备选通道** | 全天日历事件（`calendar` CLI 可用）适合纯提醒、无完成语义的场景；可后续支持 |

## 5. 中等问题：同步机制有已知破坏场景

规格用"保存 offset"做增量同步。**offset 方案会在文件被重写时失效**：

- 压缩/去重会重写文件
- 我们规划的 `love rm` / `love --refresh`（M3）也会重写
- offset 指向已失效位置 ⇒ 重复导入或漏导入

M1 目前是纯 append，暂时安全，但这个隐患已经在地平线上。

**建议**：以**幂等 upsert 为真相**，offset 只当加速缓存：

```
INSERT INTO words(...) ON CONFLICT(word) DO NOTHING   -- word 为唯一键
```

并检测 inode 变化或文件变小来判定"被重写"，触发全量重扫。

另外要回答一个规格没写的问题：**JSONL 和 SQLite，谁是真相源？** 规格暗示 JSONL 是事件日志、SQLite 是状态，但反馈只更新 SQLite——那么用户手改 JSONL 会怎样？需要明确单向数据流。

## 6. 中等：缺表、缺约束、缺策略

### 缺的表

| 表 | 为什么必须有 |
|---|---|
| `reviews` | 复习事件（时间戳、评分、当时间隔、当时是否到期）。**SRS 的算法输入，不能只有计数器。** |
| `settings` | 每日预算、发送时间、时区、暂停开关 |
| `send_log` | 幂等发送、记录"展示过什么"（用于未响应策略） |
| `tokens` | 若走 HTTP/URL 反馈，需要一次性反馈 token |
| `generated_content` | **复用 AI 生成结果**（见第 7 节） |

### 缺的约束与索引

- `words.word` 需要 `UNIQUE`（否则重复词会污染调度）
- `word_memory.next_review` 需要索引（每日查"今天到期"是最高频查询）
- 外键与级联删除策略未定义

### 缺的策略：积压与未响应 ⭐

这是规格里另一处会让系统在真实使用中崩掉的地方：

1. **新词池无限膨胀**：用户某天用 `love` 加了 20 个词，但每天只学 2 个 ⇒ 越积越多。需要 intake 上限或排队规则。
2. **复习积压**：用户 7 天不理邮件 ⇒ 到期词堆到 20 个。下一个邮件推送 20 个词，用户直接放弃。**必须有每日推送上限**，超出顺延。
3. **未反馈 ≠ 忘记**：如果用户一个按钮都不点，这些词保持 due ⇒ **永远堆积**。必须定义未响应策略（例如：连续 2 次未响应 → 保留 due 但降低推送优先级，或计为一次失败）。

这些规则应该写成一张明确的策略表，而不是留给实现者猜。

## 7. 中等：AI 层的具体化

### 范围过大

"生成故事 / 例句 / 情景对话 / 测试"——v0.1 全做会拖死项目。**v0.1 只做例句 + 释义**，其余延后。

### 缺 prompt 契约与降级路径

- 输出必须是**可校验的 JSON schema**，不是自由文本
- **AI 失败不能让当日邮件消失**：降级为纯词典版（word + ipa + chinese）

### 重要原则：生成内容必须缓存复用 ⭐

同一个词不要每天重新生成。理由不只是省钱：

1. **记忆依赖稳定的检索线索**。同一个词每天换一个新故事，反而干扰记忆编码。
2. `love` 已经验证过 cache-first 模式，直接沿用同一套思路。

⇒ 需要 `generated_content` 存储，按 word 复用。

### 后端选择：数据说话

我查了你的机器：

| 后端 | 现状 | 评价 |
|---|---|---|
| **Ollama（本地）** | 正在运行，但**只有 `nomic-embed-text`（嵌入模型，0.3GB）** | 要本地生成必须再 pull 一个对话模型（数 GB）。零边际成本、隐私最好 |
| **DeepSeek（云端）** | 已有 key，`love` 已在用，**已实测跑通** | 每天 5 个词成本可忽略，质量稳定 |

**建议**：抽象成 provider 接口，**默认沿用已验证的 DeepSeek**，Ollama 作为可选离线后端。**v0.1 不要同时支持三四个 provider**（规格列了 OpenAI Compatible / Qwen / Ollama 三种）。

## 8. 较轻但仍需回答的问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | **语言方向**只做英→中？还是也要中→英、日→中？ | schema 要不要 `lang` 字段 |
| 2 | **一词多义**：`love` M1 坚持 one word one meaning。若用户其实在学另一个义项，复习会错配。 | 要不要 `sense` 维度（建议 v0.1 不做，但要记录这个局限） |
| 3 | **词形变化**：`maintain`/`maintains`/`maintained` 会被当成 3 个词，**白白吃掉 3 份复习预算** | 要不要 lemma 归并（v0.1 至少应记录为已知问题） |
| 4 | **备份**：local-first ⇒ 磁盘坏了就没了 | 需要 `love export` 快照；纯文本已是天然备份 |
| 5 | **隐私边界**：local-first 的承诺会被"把例句发给云端 AI"打破 | 文档里必须明说：词表本地，但生成时单词会发给所配置的 provider |
| 6 | **多机**：你明显跨多机工作 | v0.1 排除云同步，但要知道 SQLite 单文件比 JSONL 更难合并冲突 |
| 7 | **daemon 是否必要** | 见第 9 节 |

## 9. 建议简化：把 daemon 降级为定时任务 ⭐

规格把 **Memory Daemon 常驻后台服务** 当成前提，代价被低估了：

- 常驻进程需要：端口/IPC 设计、崩溃自愈、日志轮转、开机自启、升级时的优雅重启
- 一个每天只干一次活的个人工具，**不值得**维护这些

**建议**：改成**定时任务一次性执行**。macOS 用 launchd（你机器上已有多个 LaunchAgent plist，加一个即可）：

```
StartCalendarInterval: 每天 07:30
程序: love daily --send
```

好处：无常驻状态、无 IPC、崩溃即"这次没跑"（下次照常）、易调试（手动跑同一条命令）。

顺带一个必须定义的策略：**笔记本睡眠导致错过时间怎么办**？launchd 会在唤醒后补跑。补跑策略需明确：**积压的多天要不要合并成一封邮件**（建议：不合并，只发当天，错过的词保持 due）。

## 10. 验收标准不可执行 ⭐

"连续运行 30 天"是人工体验，不是验收标准。应该拆成可自动化的四层：

| 层 | 内容 | 耗时 |
|---|---|---|
| **确定性单测** | 注入 fake clock，给定「初始状态 + 日期 + 反馈序列」→ 断言 `next_review`/`status` | 毫秒 |
| **Golden 测试** | 状态 → 邮件 HTML 快照比对 | 毫秒 |
| **Mock 集成** | SMTP 与 AI 都用本地 mock server（**`love` 已有这套 19 项断言的模式，直接照搬**） | 秒 |
| **时间快进模拟** | 一次性跑 30 个虚拟日，断言：不重复发送、无词丢失、积压有上限、状态收敛 | **1 秒** |

最后一条才是"连续运行 30 天"的正确验收方式——**秒级可重复，不需要真的等一个月**。

可量化指标：反馈率、到期积压数、MASTERED 词数、实际日推送量 vs 预算。

## 11. 技术选型复核

| 项 | 规格 | 我的评估 |
|---|---|---|
| Daemon | Go | ✅ 但建议改为定时一次性任务（第 9 节） |
| **Database** | **SQLite** | ⚠️ **建议 v0.1 延后**，见下 |
| AI | OpenAI 兼容 / Qwen / Ollama | ⚠️ v0.1 只留一个（建议 DeepSeek） |
| ~~Email~~ **推送通道** | ~~SMTP~~ **macOS 提醒事项（osascript）** | ✅ **已定**（§4.5）：SMTP 不再需要；**跨设备同步不在 v0.1 范围**（本机无云账号，手机为 Android） |
| HTML | Go Template | ✅ 但仍需内联样式 + table 布局（若走本地页面则不受邮件客户端限制） |
| 调度 | 未提 | ➕ 补 launchd / systemd timer |

### 关于 SQLite 的取舍（需要你决定）

`love` 目前有一个**真实优点：零第三方依赖、静态单二进制**。上 SQLite 会打破它：

- `mattn/go-sqlite3` 需要 cgo（你 `CGO_ENABLED=1`，可编译，但失去交叉编译便利）
- `modernc.org/sqlite` 纯 Go，但依赖树很大（其 `libc`/`mathutil`/`memory` 已在你 module cache 里）

而数据量其实**很小**：个人词库，1 万词以内。"今天该复习什么"在内存里过滤 < 1ms。

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. 继续用文件**（`words.jsonl` + `reviews.jsonl` 事件日志 + 派生状态） | 保持零依赖、可读可 grep、易测试、与已交付一致 | 复杂查询要自己写；多进程写入需自行加锁（**已有实现可复用**） |
| **B. 上 SQLite** | 事务、索引、SQL 查询、并发成熟 | 引入依赖 + schema 迁移负担 |

**倾向 A 用于 v0.1**，到需要复杂查询或多进程写入时再迁 B。你机器上有 `sqlite3` CLI，走 B 的话人工检查数据也方便。

**但这条取决于你的偏好**：如果你希望"用 SQL 直接查/看数据"，B 更顺手，接受依赖即可。

### 仓库结构（需要你决定）

| 方案 | 说明 |
|---|---|
| **扩展 `love`**（加子命令） | ✅ 推荐。一个二进制、一个入口、共享 `internal/cache`，避免两套 schema 同步问题。代价：需把 `main.go` 重构成 `cmd/love` |
| 新建独立仓库 | 两个二进制要同步同一份数据 schema，容易出现版本错配 |

### 砍掉 / 延后

| 砍掉 | 改成 |
|---|---|

| ❌ 故事/对话/测试 | 只做例句 + 释义 |

### 必须补

- ✅ 明确的 SRS 算法（Leitner 或 SM-2，接口可替换）
- ✅ `reviews` 事件表（算法输入）
- ✅ **认知预算的数学自洽**（复习主导新词，而非并列硬编码）
- ✅ 积压上限 + 未响应策略
- ✅ fake clock + 四层确定性测试
- ✅ AI 降级路径
- ✅ 生成内容缓存复用
- ✅ 反馈档位现在就定 3 档还是 4 档

### 修订后的 v0.1 形态

```bash
love <word>          # 加词（M1 已完成）
love <word>          # 缓存命中，复用（M1 已完成）
love daily           # 生成今日待办并写入「提醒事项」（幂等）  ← 新增：推送
love review          # 回到电脑后批量精评，终端交互           ← 新增：引擎
love review --web    # 同上，浏览器页面点选                   ← 新增：可选
love stats           # 状态分布、积压、反馈率                 ← 新增：可观测
```

全部**零依赖、可确定性测试、不需要 SMTP / 公网 / 常驻进程 / 云账号**。纯桌面闭环。

## 附：这份规格里最该保留的东西

公平地说，这份规格有三个判断**比大多数英语学习产品都清醒**：

1. **"AI 不负责替代记忆算法"** —— 绝大多数同类项目都栽在这里，让 LLM 决定复习节奏，结果既不可靠也无法测试。
2. **认知预算** —— 承认人的承受上限，把"每天 5 个"当约束而不是目标，这是能坚持一年的前提。
3. **local-first** —— 词表属于用户，可读、可备份、可手改。

需要修的不是方向，是**把缺失的那块核心（调度算法）补上，并砍掉让 v0.1 过重的外围（SMTP、常驻进程、SQLite）**。
