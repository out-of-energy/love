# Personal Language Memory Engine v0.2 — 规格评估

> 评估对象：《Personal Language Memory Engine v0.2 Architecture Specification》
> 方法：逐条对照 v0.1 评估意见，并对 Leitner 调度做 365 天仿真
> 结论：**v0.2 是一次大幅修正，我此前提的问题绝大部分被正确吸收。但引入了一个致命的数字问题——系统会在第 3–4 个月停止增长。**

---

## 0. 评分卡

| 维度 | v0.1 | v0.2 | 说明 |
|---|---|---|---|
| 数据模型 | C− | **A−** | `ipa`/`eli5` 回来了，事件日志建起来了；仍缺唯一性约束 |
| 调度算法 | D | **B+** | Leitner 明确了，接口可替换；但间隔参数有致命缺陷 |
| 认知预算 | D | **A−** | 改成"复习优先、剩余容量给新词"，机制完全正确 |
| 推送/反馈 | C− | **A** | 放弃 SMTP，本地 Reminder 不参与算法——正是修正后的方案 |
| 可测试性 | D | **A−** | Fake Clock / Golden / Replay / Stress 四层齐全 |
| 验收标准 | D | **C** | 365 天仿真很好，但**无法发现系统停滞** |
| 长期可持续性 | 未涉及 | **D** | **30 天终段间隔把词库上限锁在约 240 词** |

**一句话**：机制全对了，参数是错的。v0.2 的架构可以直接实施，但 `1/3/7/14/30` 这组间隔必须先改，否则一年后你只有 196 个词。

## 1. 修好的部分（明确肯定）

| v0.1 评估意见 | v0.2 处理 |
|---|---|
| 数据模型丢了 `ipa`/`eli5` | ✅ 回来了，且补上 `id`、`created_at` |
| 缺 `reviews` 事件表 | ✅ `reviews.jsonl` 事件日志，且记录 `algorithm`/`before_box`/`after_box` |
| 算法完全缺失 | ✅ Leitner 五盒 + 三档反馈映射 |
| `status` 与 `strength` 两套并行状态 | ✅ 状态机整个删掉，`box` 成为唯一真相源（干净） |
| **认知预算数学不成立** | ✅ **改成"到期复习优先 → 剩余容量 → 新词"**，正是建议的机制 |
| AI 生成内容不复用 | ✅ `generated/` 缓存，"同一个单词保持稳定学习上下文" |
| AI 失败无降级 | ✅ 降级为 word/ipa/eli5/chinese |
| Email 反馈够不到 localhost | ✅ 放弃 SMTP；Reminder 只提醒、**明确不参与算法** |
| daemon 过重 | ✅ 变成 `love daily` 一次性命令 |

**这九条里最关键的修正是认知预算**：从"2 新 + 3 复习并列硬编码"改成"复习优先、容量驱动"。这个机制是对的，下面的致命问题**不是机制的错，是参数选错**。

## 2. ⭐ 致命问题：30 天终段间隔把系统锁死在约 240 词

### 机制

Leitner 到 Box 5 后没有 Box 6，"掌握"只能停在原地 ⇒ **每个词每 30 天必被复习一次，永远**。

```
长期维护负载 = 词库总量 / 终段间隔
```

容量 8/天，终段间隔 30 天 ⇒ 饱和点 = 8 × 30 = **240 词**。到 240 词时，维护负载吃满全部容量，新词投放降为 0，**系统永久停滞**。

### 365 天仿真（capacity=8, max_new=3, 85% 掌握 / 10% 模糊 / 5% 忘记）

| 指标 | 每次都"掌握"（上限） | 现实分布 |
|---|---|---|
| 365 天后总词数 | **232** | **196** |
| 第 1 个月新增 | 54 | 52 |
| 第 6 个月新增 | 15 | 17 |
| **第 12 个月新增** | **4** | **4** |
| 最大积压 | 9 | 6 |

**症状**：`max_new_words: 3` 意味着每月最多可进 90 个新词，实际第 12 个月只进了 **4 个**。第 3–4 个月起，容量全部被复习吃掉，新词投放趋近于零。

`max_new_words` 这个参数**在稳态下几乎从不生效**——真正起约束作用的是 capacity。它是装饰性的。

### 我的自我更正

我在 v0.1 评估里预测过"积压爆炸"（用户不理邮件 → 到期词堆成山）。**在 v0.2 的容量机制下这个预测不成立**：仿真显示最大积压只有 6–9，容量规则把积压控制得很好。

v0.2 真实的失败模式不是**积压爆炸**，而是**增长停滞**。两者症状相反，但都会让系统失去价值。这个更正很重要，因为它意味着修复方向不是"限制推送"，而是"拉长终段间隔"。

## 3. ⭐ 验收标准抓不到这个失败

§12 的五条断言，在一个**第 12 个月只学 4 个词**的系统上**全部通过**：

| 断言 | 停滞系统是否通过 |
|---|---|
| 1. 无单词丢失 | ✅ 通过 |
| 2. 无重复爆炸 | ✅ 通过 |
| 3. 每日任务 <= capacity | ✅ 通过（正因为停滞才通过） |
| 4. 遗忘后重新进入学习流程 | ✅ 通过 |
| 5. 状态可从事件恢复 | ✅ 通过 |

**这五条全是"不出错"型断言，没有一条是"有产出"型断言。** 一个什么都不学的系统完美满足它们。

**必须补的产出型断言**：

```
6. 365 天后总词数 >= X（例如 500）
7. 最后一个月的平均日新增词 >= 1（证明系统未停滞）
8. 词库长期上限 >= Y（capacity × 终段间隔 >= 目标词汇量）
```

第 8 条尤其重要——它是**能在 1 秒内算出来的设计期检查**，不用跑仿真就知道参数对不对。

## 4. 数据模型：一处回归 + 若干待定

### 4.1 ⚠️ 回归：`words.jsonl` 丢了唯一性约束

v0.2 用 `id: uuid` 作为主键，但**没有任何东西阻止同一个词被加两次**：

```
love add maintain    →  uuid-A
love add Maintain    →  uuid-B      ← 同一个词，两条记录
```

后果：同一个词在调度器里占**两份**复习预算，学习量翻倍，且两者状态必然分叉（一个好一个坏）。

**这是从 M1 的倒退**：`love` M1 已有 `Normalize()` + 首条命中优先的去重保证，v0.2 引入 uuid 后把它丢了。

**修法**：`word`（规范化后）为唯一键，uuid 只是稳定标识：

```
words.jsonl 唯一约束：Normalize(word)
重复 add → 返回已存在的 id，不新建（幂等）
```

### 4.2 ⚠️ `rating` 到底是 3 档还是 4 档？

§5 定义 **3 个标签**（忘记 / 模糊 / 掌握），但 §4.2 的事件示例写的是：

```json
{"rating": 4, ...}
```

`4` 从哪来？如果映射是 忘记=1/模糊=2/掌握=3，那 `4` 无法解释。这看起来是**半采纳了我"现在就定 3 档还是 4 档"的建议**。

这个必须现在定死，因为它同时影响：事件 schema、复习 UI、未来 FSRS 迁移（FSRS 用 Again/Hard/Good/Easy 四档）。

**建议**：既然 `reviews.jsonl` 已带 `algorithm` 字段，就**直接按 4 档存储**（1=忘记 2=模糊 3=掌握 4=轻松），Leitner 只用前 3 档。这样 v0.3 上 FSRS 时不需要迁移历史事件。

### 4.3 `memory.json` 的三个未定义点

1. **它怎么装多个词？** §4.3 的示例是**单个对象** `{"word_id":"uuid","box":3,...}`，但显然要存全部词。是数组？还是 `{word_id: state}` 映射？**必须写明**。
2. **写入原子性**：每次复习都要重写整个文件。中途崩溃 → 文件损坏 → 全部记忆状态丢失。**必须 temp 文件 + rename 原子替换**。
3. **陈旧检测**：`memory.json` 是缓存，但系统怎么知道它过期了（崩溃、手改）？**建议在文件里记录"已消费的事件数/哈希"**，加载时对不上就自动重放 `reviews.jsonl` 重建。

顺带：Stress Test 目标 10000 词，那时每次复习重写 1MB 文件虽然可行，但**重放 10 万条事件**才恢复状态，需要明确这条路径的耗时预算。

### 4.4 `box` 与 `stability` 并存 —— 老问题重现

`memory.json` 同时有 `box: 3` 和 `stability: 12`。但 Leitner 下 **`box` 完全决定间隔**，`stability` 无定义、无来源、无更新规则。

这正是我在 v0.1 评估里批评过的"两套并行状态"问题，换了个形式回来了。它一定会漂移（比如 `box=3` 但 `stability=40`）。

**修法**：二选一。
- 若坚持 Leitner：**删掉 `stability`**；
- 若想为 FSRS 预留：明确定义为**派生值** `stability = interval(box)`，并注明"v0.2 只读不写"。

### 4.5 每日选哪几个到期词？排序未定义

到期 20 个、容量 8 个，**选哪 8 个？** 规格没写。这有两个后果：

1. **破坏确定性测试**。§11 的 Fake Clock 与 Event Replay 测试要求同样输入得到同样输出；选择顺序不确定 ⇒ 测试会随机失败。**必须在规格里写死排序规则**。
2. 影响学习效果（最逾期的该优先，还是低 Box 的优先？）。

**建议**：`按 next_review 升序（最逾期优先），同日则按 box 升序`。

## 6. 修正建议（含仿真数据）

容量 8、max_new 3、85/10/5 分布、365 天：

| 配置 | 365 天词量 | 末 30 天新增 | 长期上限 |
|---|---|---|---|
| **v0.2 原案** `1/3/7/14/30`, cap 8 | **196** | **4** | **240** |
| 长尾 `…/60/120/240`, cap 8 | 325 | 22 | 1920 |
| 长尾 + cap 12 | 474 | 27 | 2880 |
| 长尾 + cap 16 | 630 | 35 | 3840 |
| **推荐** `1/3/7/14/30/90/180/365`, cap 16, max_new 4 | **665** | **37** | **5840** |

两个关键洞察：

1. **终段间隔决定长期上限**（capacity × 终段间隔）。240 词对一个要跑数年的系统是致命的；改成长尾后上限变成数千。
2. **第一年的吞吐主要受前几盒限制**，不是终段。所以间隔尾巴要长、`capacity` 也要够（8 → 16）。

**具体建议参数**：

```yaml
intervals: [1, 3, 7, 14, 30, 90, 180, 365]   # 8 盒，尾巴拉到一年
daily_capacity: 16                            # 8 偏小
max_new_words: 4                              # 承认它很少成为约束
```

> 备注：`1/3/7/14/30/90/180/365` 已经接近 SM-2 的自然形态。如果打算 v0.3 上 FSRS，可以现在就把 `Scheduler` 接口按"输入 (状态, 时间) → 输出 (间隔)"设计好，Leitner 只作为第一实现。

## 8. 结论

v0.2 的**架构已经可以动手实施了**——事件溯源、容量驱动预算、可替换调度器、本地提醒、四层测试，这几个决定都是对的，我此前的意见几乎全部被正确吸收。

**唯一的拦路石是参数。** `1/3/7/14/30` + `capacity 8` 会把词库锁在约 240 词，而且第 12 个月只新增 4 个词——而现有的五条验收断言**全部无法发现这一点**。

改三行配置即可：

```yaml
intervals: [1, 3, 7, 14, 30, 90, 180, 365]
daily_capacity: 16
max_new_words: 4
```

再补一条产出型验收断言（`365 天后总词数 >= 500`），v0.2 就可以开工了。
